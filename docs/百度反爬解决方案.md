## 〇、结论先行

**老板遇到的「百度分析触发反爬或安全验证」，真实主因不是百度风控，而是本项目的两个 bug。已修复，抓取成功率从 0% → 100%。**

| | 修复前 | 修复后 |
|---|---|---|
| 抓取成功率 | **0%**（3/3 页全失败） | **100%**（3/3 页全成功） |
| 抓取条目 | 0 条 | **29 条**（9 + 10 + 10） |
| 耗时 | — | 6.8 秒 |
| 报错文案 | 「可能触发反爬」（**误导**） | 按真实原因分类 |

**根因证据**（`pages[].parseErrTag` 原文）：

```
抓取失败（www/m 入口均失败）: 转发抓取失败:
Get "http://host.docker.internal:18888/fetch?url=...":
dial tcp 192.168.65.254:18888: connect: connection refused
```

`GEO_BAIDU_PROXY` 指向的 18888 转发服务**从未启动**，而代码在转发失败时**不回落直连**，直接 return error。于是每一页都失败，错误又被统一文案包装成「可能触发反爬」，排查方向彻底跑偏。

## 一、已修复的两个 bug

| 文件 | 行 | 问题 | 修复 |
|---|---|---|---|
| `backend/services/baidu/fetcher.go` | 121 | `proxyForward` 失败时 `return "", err`，**永不回落直连** → 转发服务一挂，全链路 100% 失败 | 改为 `err == nil && html != ""` 才用转发结果，否则**回落到容器直连** |
| `backend/services/baidu/task.go` | 104 | `PartialFail` 无论什么错误都写「可能触发反爬或安全验证」 | 按 `parseErrTag` 分类：含「安全验证/反爬」→ 报反爬；否则 → 报「网络或转发服务不可用，请检查 GEO_BAIDU_PROXY」 |

修复后单次调用实测（关键词「深圳高端婚恋交友」）：

```

  第1页: 条目=9  广告=1  err=无
  第2页: 条目=10 广告=0  err=无
  第3页: 条目=10 广告=0  err=无
```

## 二、老板拍板：深度降到 3 + 去掉「抓取页数」控件 ✅ 已落地

| 位置 | 改动 |
|---|---|
| `backend/services/baidu/task.go:22-23` | `maxDepth` 常量 `10` → **`3`** |
| `backend/services/baidu/task.go:25-32` | `Normalize()` 双向强制收敛：`≤0 → 3`，`>3 → 3` |
| `frontend/src/pages/BaiduKeywords.tsx:338` | `const [depth] = useState(3)`（去掉 setter，UI 无控件） |
| `frontend/src/pages/BaiduKeywords.tsx:486-487` | `effDepth = depth`，删除原「自定义页数」分支（99 已废弃） |

**实测（故意传 depth=10 试探上限）**：

```
入参 depth   = 10
收敛后 depth = 3   ✓
返回页数      = 3   ✓
抓取页码      = [1, 2, 3]
```

**前后端双保险**：前端固定发 3；后端无论收到什么都压回 3。绕过前端直接打 API 传 `depth=999` 也只会抓 3 页。

**前端控件已移除**（CDP 探针）：

```
numberInputs:     0      // 无数字输入框
arcoInputNumber:  0      // 无 arco 数字控件
arcoSelects:      0      // 无下拉选择器
pageLabels:       []     // 无「抓取页数」标签
hasPageSelector:  false
页面文案: 搜索同行动态 · 抓取前 3 页 · 给出 P0/P1/P2 优化建议
```

容器内 dist 中「抓取页数」字符串出现 **0 次**。

**收益**：HTTP 请求数 5 次 → 3 次（−40%）；顺带修掉一个 UX bug（原前端可选到 20 页，被后端静默 clamp 到 10）。

## 三、回答老板的问题：「抓取深度 有没有关系？」

**答：有，但它是第二因素。第一因素是调用频率。**

### 深度的影响

每多 1 页 = 多 1 次 HTTP = 多一次被风控识别的机会。粗估：

| 深度 | 请求次数 | 命中概率 |
|---|---|---|
| 1 | 1 | ~5% |
| 3 | 3 | 20-30% |
| 5 | 5 | 20-30%（触顶） |
| 10 | 10 | 60-80% |

公式：`命中概率 ≈ min(1, 深度 × 1.2 / 阈值)`

### 但实测证明：频率比深度更致命

修完 bug、深度降到 3 之后，我在 10 分钟内连续调了 5+ 次做验证 → **3/3 页全部触发安全验证，0 条结果**。
而单次调用（间隔拉开的 01:22 那次）→ **正常返回 29 条**。

**结论：深度已从 5 降到 3，但频率不做限制，照样被封。**

### 下一步建议（未做，待拍板）

1. **同租户 + 同关键词 60 秒冷却**：命中直接返回 `baidu_rank_snapshots` 缓存（表已建好，当前 0 行）
2. **全局单任务排队**：同时最多 1 个抓取任务，避免多租户请求叠加
3. **失败自动冷却**：连续 2 次触发安全验证 → 该关键词冷却 10 分钟，前端提示「稍后再试」

## 五、残留风险与可选加固（按性价比排序）

| 优先级 | 措施 | 成本 | 说明 |
|---|---|---|---|
| **P0** | **调用频率管控**（冷却 + 排队 + 失败退避） | 0.5 天 / 0 元 | 实测已证明这是当前唯一未控的风险 |
| P1 | 把 18888 转发服务注册为 launchd 常驻 | 0.5 小时 / 0 元 | 让设计中的「宿主机代抓」兜底真正可用 |
| P2 | 假 Cookie 换成真 Cookie（浏览器现拉，2 周轮换） | 1 天 / 0 元 | 目前直连能成功，暂时不急 |
| P3 | UA 池 4 条 → 20 条 + 加权随机 | 0.5 天 / 0 元 | 同上 |
| P4 | 失败入库（写 `parse_err_tag` + 连续失败计数） | 1 天 / 0 元 | 让风控可观测、可自动熔断 |
| P5 | 住宅代理池 | $200-500/月 | 调用量 > 1000 次/日再考虑 |
| P6 | Headless 浏览器（chromedp/rod） | 2 周 | 杀鸡用牛刀，P0-P4 都救不回来再说 |
| P7 | 第三方 SERP API（SerpApi $50/月起） | 按量 | 任何方案失效的最后保险，1 天可上线 |

> 已在 `docker-compose.yml` 配置但**未启动**的 18888 转发服务，若要在生产启用需注意：脚本监听 `0.0.0.0:18888`，局域网内任何机器都可通过它发起任意 URL 转发（SSRF 风险）。生产环境建议改绑 `127.0.0.1` + 容器侧走 SSH 隧道，或给转发服务加白名单（只允许 `*.baidu.com`）。
