# LinkGeo 客户效果监控小程序 · 技术方案

> 版本 v1.0 · 2026-09-05 · 太湖一号
> 目标：在 LinkGeo 系统框架内，开发一个**微信小程序**，让分站客户随时在手机上查看自己品牌的 GEO 优化效果。

---

## 一、产品定位

| 项 | 说明 |
|---|---|
| 名称 | LinkGeo 效果监控（暂定，可复用品牌名） |
| 形态 | 微信小程序 |
| 用户 | 分站客户（婚恋企业老板/运营），每人看自己品牌的优化效果 |
| 核心价值 | 把「我们帮你做了 GEO 优化」变成**客户手机上一眼可见的效果**，提升交付可信度与续费率 |
| 数据来源 | 复用 LinkGeo 后端已有数据（六项指标 / 竞品声量 / 效果归因 / 信源 / 站内信） |

一句话：**小程序是 LinkGeo「效果验收」模块的移动端窗口，只读展示为主，不做重操作。**

---

## 二、功能清单

### MVP（第一版，够用即上线）

| 模块 | 功能 | 复用的后端数据 |
|---|---|---|
| 登录 | 微信登录 + 绑定分站账号（一次绑定，之后免登） | 新增 |
| 效果总览 | 六项核心指标卡片：品牌出现率、推荐率 TOP3、引用率、事实一致率、品牌声量、竞品声量 | `/geo/intel` |
| 效果趋势 | 品牌出现率趋势曲线（近 7/30 天切换） | `/geo/intel`（trend 字段） |
| 竞品对标 | 竞品声量排行 + 首推率 | `/geo/gaps` |
| 效果归因 | 前后期对比（before/after，涨跌一目了然） | `/geo/compare` |
| 工作状态 | 最近巡检时间 + 覆盖率（绿点/灰点） | `/geo/intel` |
| 消息中心 | 站内信列表 + 未读角标 | `/notifications/*` |

### 迭代版（第二版）

| 模块 | 说明 |
|---|---|
| Token 余额 + 充值 | 余额展示 + 套餐选择（`/points`、`/recharge/plans`），支付走微信小程序支付 |
| 报告查看 | 生成报告 H5 链接预览 |
| 订阅消息 | 效果下降 / 巡检完成时微信订阅消息推送（替代站内信被动查看） |

## 三、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 小程序前端 | **Taro**（React 语法） | 现有团队是 React，零学习成本；一套代码可发小程序/H5 |
| 后端 | **复用 LinkGeo Go 后端** | 数据、鉴权、租户隔离全部现成，只加小程序专用接口 |
| 鉴权 | 微信登录（`wx.login` → `code2session`）+ 绑定分站账号 | 符合小程序习惯，免输密码 |
| 图表 | ECharts（小程序版） | 与 Web 端同一套图表能力 |
| HTTPS | Nginx 反代 + 证书 | 小程序强制 HTTPS，后端只暴露 443 |

**关键决策：小程序是「只读展示层」，所有数据、逻辑、权限都在现有 LinkGeo 后端，小程序不含任何业务逻辑。**

---

## 四、系统架构

```
微信小程序 (Taro)
   │  HTTPS (JSON)
   ▼
Nginx（HTTPS 反代 + 证书）
   │  HTTP (内网)
   ▼
LinkGeo 后端 (Go, 单二进制)
   │  复用 AdminOnly 中间件（JWT → tenant_id 隔离）
   ▼
SQLite (geo-tool.db)
```

- **数据隔离**：沿用现有 `JWT` + `AdminOnly()` 中间件，小程序登录拿到的 token 同样带 `tenant_id`，天然隔离，客户只能看自己分站的数据。
- **零改动复用**：`/geo/*`、`/dashboard/*`、`/notifications/*`、`/points` 等接口直接可用，小程序只是换了个前端壳子调用它们。

## 五、接口设计

### 5.1 复用现有接口（无需改动）

| 接口 | 用途 |
|---|---|
| `GET /geo/intel?days=N` | 六项指标 + 趋势 |
| `GET /geo/gaps?days=7` | 竞品声量 + 首推率 |
| `GET /geo/compare` | 效果归因前后期 |
| `GET /geo/channels` | 阵地地图（可选展示） |
| `GET /notifications` + `/unread_count` | 站内信 |
| `GET /points` | Token 余额 |
| `GET /recharge/plans` | 套餐列表 |

### 5.2 新增接口（小程序专用，约 3 个）

**① 微信登录**（小程序第一次进来）
```
POST /api/miniapp/login
body: { code: "wx.login 返回的 code" }
→ 后端调微信 code2session 拿 openid
→ 若 openid 已绑定分站账号 → 返回 JWT
→ 若未绑定 → 返回 { need_bind: true }
```

**② 绑定分站账号**（首次）
```
POST /api/miniapp/bind
body: { code: "wx code", bind_code: "总后台生成的绑定码" }
→ 校验绑定码 → 绑定 openid ↔ 分站账号 → 返回 JWT
```

**③ 聚合首页**（一次拉取，减少小程序请求数）
```
GET /api/miniapp/home
→ 聚合返回：六项指标 + 趋势 + 竞品声量 + 未读数
（内部并行调 geo/intel、geo/gaps、notifications/unread_count）
```

> 绑定码：总后台「客户管理」里为每个分站生成一次性绑定码（或二维码），客户扫码/输码完成绑定。这是打通「小程序 openid」和「分站账号」的桥梁。

## 六、数据库改动（极少量）

新增一张表 `miniapp_bindings`：

| 字段 | 说明 |
|---|---|
| openid | 微信 openid（唯一） |
| tenant_id | 绑定的分站 |
| user_id | 绑定的分站账号 |
| bind_code | 一次性绑定码（绑定后失效） |
| created_at | 绑定时间 |

仅此一张表，不动现有 40+ 张表的任何结构。

## 八、需要老板准备的前置条件（阻塞项）

| 项 | 说明 | 获取方式 |
|---|---|---|
| **微信小程序 AppID** | 小程序必须有主体 | [微信公众平台](https://mp.weixin.qq.com) 注册小程序（个人/企业主体均可，企业主体才能用支付） |
| **HTTPS 域名 + 证书** | 小程序强制 HTTPS | 服务器域名 + 免费证书（Let's Encrypt）或云厂商证书 |
| 小程序名称/头像/类目 | 上线资料 | 注册时填写 |

> 说明：小程序开发**不依赖**这些前置条件就能启动（可用「测试号」+ 内网调试先把功能做出来），但**正式发布**必须要有 AppID 和 HTTPS 域名。

## 九、风险与边界

1. **微信登录依赖 AppID/Secret**：没有正式 AppID 前，可用「测试号」开发，逻辑不变。
2. **小程序支付门槛**：Token 充值若走微信支付，需要企业主体 + 微信支付商户号（个人主体不支持支付）。**建议 MVP 先只做「余额展示 + 跳转 Web 充值」，支付留到迭代版**。
3. **数据实时性**：小程序展示的指标依赖巡检数据，巡检是 60 分钟一轮，小程序读的是最近一轮结果，无需额外实时计算。
4. **合规**：小程序只读展示，不做抓取/群发，规避平台风控，与 Web 端同一套合规边界。

---

## 十、结论

- 小程序是**纯展示层**，95% 的接口和数据现成，开发量集中在「微信登录绑定 + 3 个聚合接口 + 小程序前端页面」。
- 建议 **MVP 先做：登录 + 效果总览 + 趋势 + 竞品对标 + 效果归因 + 消息中心**（约 2 周），支付和订阅消息放迭代版。
- 唯一硬阻塞是**微信小程序 AppID + HTTPS 域名**，需要你这边先注册小程序。
