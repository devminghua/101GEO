# 平台 ID 跨租户冲突 —— 彻底治理方案

> 编制：太湖一号　|　日期：2026-09-06　|　背景：AI 平台分站化改造后暴露

## 一、问题根因

### 1.1 表结构

`ai_platforms` 主键是**自增 ID**，且每个 `tenant_id` **独立自增**：

| tenant_id | 平台 | ID |
|---|---|---|
| 0（全局）| DeepSeek | 1 |
| 0（全局）| 豆包 | 2 |
| ... | ... | ... |
| 0（历史）| Ollama | 10（已删，但数据残留）|
| 1（潼羽科技）| DeepSeek 副本 | **10** ← 撞车 |
| 1（潼羽科技）| 豆包 副本 | 11 |

### 1.2 冲突表现

`check_results.platform_id` 只存一个数字，无法区分「结果来自哪个租户的平台」。分站化后，同一分站的结果混存了「全局平台 ID（1-9）」和「分站副本 ID（10-15）」，导致：

```
platform_id = 10  → 同时包含 DeepSeek(89条) + Ollama(9条)  ← 严重串数据
```

### 1.3 量化（demo 分站 tenant_id=1）

| platform_id | 实际平台 | 条数 | 状态 |
|---|---|---|---|
| 1-9 | 全局平台（含已停用 OpenAI=6）| 1431 | 旧数据 |
| 10 | DeepSeek 副本 + **Ollama（串）** | 89 + 9 | 冲突 |
| 11-15 | 分站副本 | 294 | 新数据 |

## 二、方案对比

| 方案 | 思路 | 优点 | 缺点 | 改动量 |
|---|---|---|---|---|
| **A. 全用 name 关联** | check_results 只用 platform_name | 简单彻底 | 改名断链、重名风险 | 小（已基本完成）|
| **B. 全局唯一 ID** | 平台 ID 全局唯一（UUID/雪花）| ID 稳定、查询快 | 迁移大、影响面广 | 大 |
| **C. 复合键** | (tenant_id, platform_id) 关联 | 同租户不冲突 | 继承场景仍乱 | 中 |
| **D. A + 数据清洗 + 约束** | name 关联 + 清洗脏数据 + 唯一约束 | 彻底、稳妥 | 需清洗一次 | 中 |

---

## 三、推荐方案 D（稳妥彻底）

在「已完成的 name 关联改造」基础上，补齐三件事：

### 3.1 数据清洗（一次性）

把 `check_results.platform_id` 里**冲突的数据**重新映射：

```sql
-- 原则：platform_id 已不可信，统一以 platform_name 为准
-- 1) 把「分站副本」的 platform_id 映射回「全局平台」的 ID（同一 name 取最小全局 ID）
-- 2) 停用平台（OpenAI/Ollama）的历史数据单独标记，不参与统计
```

目标：同一 `platform_name` 只对应**一个** platform_id（全局平台的 ID），消除 10 号冲突。

### 3.2 唯一约束

给 `ai_platforms` 加唯一约束 `(tenant_id, name)`，防止同名平台在同一租户内重复（从根上防止再次混乱）。

### 3.3 改名断链保护

- `check_results.platform_name` 保留**快照**（巡检时的平台名），不随平台改名而变。
- 平台改名时，前端提示「历史数据仍按旧名关联，新巡检用新名」。

---

## 四、实施步骤

| 步骤 | 动作 | 风险 |
|---|---|---|
| 1 | 备份 PG（pg_dump）| 无 |
| 2 | 清洗 check_results.platform_id（按 name 重映射）| 低（有备份）|
| 3 | ai_platforms 加 (tenant_id,name) 唯一约束 | 低 |
| 4 | 回归验证 dashboard/geo/intel/小程序统计 | 低 |
| 5 | 文档记录「平台 ID 不再作为关联键」约定 | 无 |

---

## 五、长期约定（防复发）

1. **关联键 = platform_name**（稳定唯一），platform_id 仅作记录，不作关联。
2. **分站复制平台时**：复制后立即把副本的引用统一回全局平台 ID，或干脆不复制 ID、只复制「启用+Key」到分站配置层。
3. **新增平台**：强制校验 `(tenant_id, name)` 唯一。
4. **平台停用**：历史数据保留但标记 excluded，统计时过滤。

---

## 六、是否要做「全局唯一 ID」（方案 B）？

**结论：不推荐现在做。**

- 当前系统单实例部署，name 关联已经足够正确。
- 全局唯一 ID 需要改主键生成（雪花/UUID）+ 全量迁移，收益低、风险高。
- 只有当「未来要跨库合并 / 多实例分布式」时才值得升级。

> 建议：本次按方案 D 落地，把 name 关联 + 数据清洗 + 唯一约束做扎实；全局唯一 ID 留作远期演进项。
